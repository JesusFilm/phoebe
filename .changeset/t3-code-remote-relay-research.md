Research record: how T3 Code reaches remote machines (docs/research/t3-code-remote-relay.md, issue #498). Read from the `pingdotgg/t3code` source and its shipped docs at commit `e16b8b05`. T3 Connect's relay is a control plane only: a Cloudflare Worker with Postgres that links environments to a Clerk account, provisions a Cloudflare Tunnel per environment, brokers a one-time bootstrap credential and delivers push, and never carries application traffic. The environment binds loopback and spawns `cloudflared tunnel run`, so the dial-out goes to Cloudflare's edge and clients reach the tunnel hostname directly over Effect RPC on a JSON WebSocket at `/ws`. The note records the four routes to a T3 environment, the transport and session semantics (5-minute socket ticket, 30-day session, a 3s/4s/8s/16s reconnect ladder with one retry owner, credential refresh that does not drop the socket), the split between Clerk cloud identity and environment pairing grants, and the mint exchange that keeps the relay from ever holding an environment session. It closes with which parts transfer to Phoebe's relay and which do not: the dial-out shape, one retry owner, a per-deployment signing key and nonce-bound signed requests transfer; the pure control-plane split does not, because Phoebe's deployments have no public hostname, so its relay must also be the data path.
