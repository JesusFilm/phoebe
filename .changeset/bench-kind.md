New opt-in catalog kind, `bench` (`path: "phoebe-agent/kinds/bench"`). Declare it in a pipeline of its own with one slot. When a person adds the `phoebe:bench` label to an open PR, the kind replays the deployment's suite with two contenders through the same `runBench` that `phoebe bench run` uses. `main` has the default branch's `issues` prompt, provider, model and effort, and `pr` has the PR head's. Prompts are read as text through git. Each side's settings come from evaluating that commit's governing config in a child process whose environment holds no GitHub credential and no provider key, and only the resolved settings come back, as JSON. The kind posts a new comment with both contenders side by side: test pass rate, no-change count, median tokens, median cost, and judge verdicts when a judge is set. The comment also lists unstable fixtures and gives the total cost, and it notes when the PR changes `AGENTS.md` or skills, which bench does not measure yet. Then the kind removes the label. A deployment with no suite gets a comment with the `phoebe bench select` command, and a PR that changes nothing bench can measure gets a comment saying so. Neither runs a bench. An interrupted bench keeps its label and runs again. Options: `suite` (required), `maxFixtures` (default 10, the newest), `repeat` (default 1) and `judge`, catalogued as `PHOEBE_BENCH_SUITE`, `PHOEBE_BENCH_MAX_FIXTURES`, `PHOEBE_BENCH_REPEAT`, `PHOEBE_BENCH_JUDGE_PROVIDER` and `PHOEBE_BENCH_JUDGE_MODEL`. The kind starts no agent of its own, so its unit records carry no agent runs, and its trials stay in `bench/<runId>/`. The GitHub client gains `listLabeledPrs` and `removeUnitLabel`. An observer PR proposal that edits `prompts/` or the governing config now says in its body that the `phoebe:bench` label measures it. The observer never adds the label. The docs describe the kind, give a by-hand recipe for a two-contender bench config, and explain why no CI workflow template ships.
