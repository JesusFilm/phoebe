# Google sign-in for a self-hosted single-operator web service

Research notes, 2026-09-09. All claims verified against primary sources (Google Identity
docs, the OpenID Connect Core spec, the IETF drafts/RFCs, Node's own docs, and the
libraries' own docs, source, and npm registry metadata); each claim cites the owning
source. Context: ticket #499, part of the relay map (#497). The relay is a minimal
self-hosted Node 24 service with one operator; it needs to know who is at the browser,
gate access to a short allowlist, and do so with as little code and as few dependencies as
the job allows.

## 1. Which flow

Use the **OpenID Connect server flow** (OAuth 2.0 authorization code grant, with the
`openid` scope so Google returns an ID token). Google's OIDC guide names it the flow that
"allows the backend server of an application to verify the identity of the person using a
browser or mobile device", and it is the one that uses the client secret. Source:
https://developers.google.com/identity/openid-connect/openid-connect

The guide's six steps, verbatim in spirit:

1. Create an anti-forgery `state` token — "a string of 30 or so characters constructed
   using a high-quality random-number generator" — and hold it in the user's session.
2. Redirect to `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`,
   `response_type=code`, `scope` (which "must begin with the `openid` value and then
   include the `profile` value, the `email` value, or both"), `redirect_uri`, `state`, and
   `nonce` ("a random value generated by your app that enables replay protection").
3. On the callback, "confirm that the `state` received from Google matches the session
   token you created."
4. POST `code`, `client_id`, `client_secret`, `redirect_uri`, `grant_type=authorization_code`
   to the token endpoint; the response carries `id_token` and `access_token`.
5. Read the user's identity from the ID token (a JWT).
6. Look the user up and establish your own session.

Source for all six: https://developers.google.com/identity/openid-connect/openid-connect

Add PKCE. Google's discovery document advertises `code_challenge_methods_supported:
["plain","S256"]` (https://accounts.google.com/.well-known/openid-configuration), and RFC
7636 defines `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))` with a
43–128 character verifier; its purpose is defeating authorization-code interception
(https://datatracker.ietf.org/doc/html/rfc7636). PKCE is not required for a confidential
web client, but it costs one hash and removes a class of attack.

Endpoints, all from the discovery document
(https://accounts.google.com/.well-known/openid-configuration):

| Metadata                 | Value                                              |
| ------------------------ | -------------------------------------------------- |
| `issuer`                 | `https://accounts.google.com`                      |
| `authorization_endpoint` | `https://accounts.google.com/o/oauth2/v2/auth`     |
| `token_endpoint`         | `https://oauth2.googleapis.com/token`              |
| `userinfo_endpoint`      | `https://openidconnect.googleapis.com/v1/userinfo` |
| `jwks_uri`               | `https://www.googleapis.com/oauth2/v3/certs`       |
| ID token signing alg     | `RS256`                                            |
| `scopes_supported`       | `openid`, `email`, `profile`                       |

Do not use the implicit flow or the "Sign In With Google" JavaScript button for this; both
put identity assertions in the browser first and require a separate server-side token
verification step anyway (https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).
The server flow ends with the ID token already on the server.

## 2. Google Cloud setup, cost, and verification

**Project and client.** "Visit the Google API Console to obtain OAuth 2.0 credentials such
as a client ID and client secret" (https://developers.google.com/identity/protocols/oauth2).
Under Google Auth Platform: create or select a project, fill in Branding (app name,
support email, authorized domains), choose the audience, then "Click **Create client** and
for **Application type** select **Web application**." For sign-in the docs say "default
scope (email, profile, openid) is sufficient, you don't need to add any sensitive scopes."
Source: https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid

**Redirect URI rules.** "Redirect URIs must use the HTTPS scheme, not plain HTTP.
Localhost URIs (including localhost IP address URIs) are exempt from this rule." Raw IP
hosts (other than localhost), userinfo, fragments and path traversal are rejected.
Source: https://developers.google.com/identity/protocols/oauth2/web-server

**Client secret.** "Don't store the client_secret.json file in a publicly-accessible
location ... store the client_secret.json file outside of your source tree."
Source: https://developers.google.com/identity/protocols/oauth2/web-server

**Cost.** None of the OAuth/OIDC pages mention pricing (checked:
https://developers.google.com/identity/protocols/oauth2,
https://developers.google.com/identity/protocols/oauth2/web-server,
https://developers.google.com/identity/openid-connect/openid-connect). Creating a Cloud
project does not require a billing account — the console's billing selector is optional at
creation and only shown to holders of the Billing Account User role
(https://docs.cloud.google.com/resource-manager/docs/creating-managing-projects). The only
API the relay calls is the OAuth token endpoint, which needs no enabled API and no
billing. Practical reading: free.

**User type and publishing status** (https://support.google.com/cloud/answer/15549945):

- _Internal_ user type "limit[s] authorization requests to members of the organization" —
  only available when the project sits in a Google Workspace / Cloud organization.
- _External_ + _Testing_: "limited to up to 100 test users listed in the OAuth consent
  screen", and authorizations expire after seven days. The seven-day expiry is about
  refresh tokens: a Testing project "is issued a refresh token expiring in 7 days, unless
  the only OAuth scopes requested are a subset of name, email address, and user profile"
  (https://developers.google.com/identity/protocols/oauth2). A sign-in-only relay is
  inside that exception and never stores a refresh token anyway.
- _External_ + _In production_: "available to any user with a Google Account", reached by
  pressing **Publish app**.

**Verification.** "If your app utilizes only non-sensitive scopes, it is not mandatory for
your app to complete the app verification process." `openid`, `email`, `profile` are
non-sensitive. Brand verification is only needed "if you want your application logo and
application name to be visible to users on the consent screen"
(https://support.google.com/cloud/answer/13463073,
https://support.google.com/cloud/answer/10311615). The "Unverified apps" warning and the
"100 new users in total" cap attach to apps requesting sensitive or restricted scopes
(https://support.google.com/cloud/answer/15549945). Brand verification, if wanted, "typically
takes a few minutes" automated, or 2–3 business days manual
(https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification).

Net for a single-operator relay: External user type, keep it in Testing with the
operator's account(s) listed as test users, no verification, no cost. Publishing is a
button press later if the allowlist ever exceeds 100 people, and still needs no
verification for these scopes.

## 3. Obtaining a verified email

Request `scope=openid email` (add `profile` only if you want `name`/`picture`). "If the
`email` scope value is present, the ID token includes `email` and `email_verified`
claims." No userinfo call is needed for email; the userinfo endpoint exists but adds a
round trip for the same data
(https://developers.google.com/identity/openid-connect/openid-connect).

What `email_verified` means, per the spec: "True if the End-User's e-mail address has been
verified; otherwise false. When this Claim Value is true, this means that the OP took
affirmative steps to ensure that this e-mail address was controlled by the End-User at the
time the verification was performed. The means by which an e-mail address is verified is
context specific." (OpenID Connect Core 1.0 §5.1,
https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims). Google's own wording
is "True if the user's email address has been verified; otherwise false"
(https://developers.google.com/identity/openid-connect/openid-connect). Treat
`email_verified !== true` as no email.

Identity key: Google says `sub` is "unique among all Google Accounts and never reused ...
Use `sub` within your application as the unique-identifier key for the user", and "you
**shouldn't** use the `email` field in the ID token as a unique identifier for a user"
(https://developers.google.com/identity/openid-connect/openid-connect). The spec agrees:
`sub` is "locally unique and never reassigned within the Issuer" while emails can change
hands (§2 and §5.7, https://openid.net/specs/openid-connect-core-1_0.html). Consequence for
an allowlist: the operator types emails (that is what a human knows), but the record
stores `sub` once seen, and later matches on `sub` first, email second.

Workspace domains: the `hd` claim is "provided only if the user belongs to a Google Cloud
organization", and "You must check this claim when restricting access to a resource to
only members of certain domains" — a domain allowlist compares `hd`, not the email suffix
(https://developers.google.com/identity/openid-connect/openid-connect).

## 4. ID token verification

Google's required checks
(https://developers.google.com/identity/openid-connect/openid-connect and
https://developers.google.com/identity/gsi/web/guides/verify-google-id-token):

1. Signature, using the keys at `jwks_uri`. "Since Google changes its public keys only
   infrequently, you can cache them using the cache directives of the HTTP response."
2. `iss` equals `https://accounts.google.com` or `accounts.google.com`.
3. `aud` equals your client ID.
4. `exp` has not passed.
5. If you passed `hd`, the `hd` claim matches.

Plus, from the spec (§3.1.3.7, https://openid.net/specs/openid-connect-core-1_0.html): "If a
nonce value was sent in the Authentication Request, a nonce Claim MUST be present" and must
match; check `iat` against a reasonable window.

Two facts shape the library decision:

- **Signature verification is optional in the server flow.** OIDC Core §3.1.3.7 rule 6
  allows a client that obtained the ID token directly from the token endpoint over TLS to
  rely on TLS server validation instead of checking the JWS. oauth4webapi (the engine
  under openid-client) documents exactly this: "Validating signatures of JWTs received via
  direct communication between the Client and a TLS-secured Endpoint (which it is here) is
  not mandatory since the TLS server validation is used to validate the issuer instead of
  checking the token signature. You only need to use this method for non-repudiation
  purposes." (`validateApplicationLevelSignature`,
  https://github.com/panva/oauth4webapi/blob/main/src/index.ts). The relay gets its ID
  token from that direct exchange, so it needs claim checks, not a JWKS client.
- **The tokeninfo endpoint is for debugging only.** `https://oauth2.googleapis.com/tokeninfo?id_token=...`
  "is useful for debugging but for production purposes, retrieve Google's public keys
  from the keys endpoint and perform the validation locally"; "requests to the debugging
  endpoint may be throttled" (https://developers.google.com/identity/openid-connect/openid-connect).

If you do want signature verification (defence in depth, or because you ever accept an ID
token from anywhere other than the token endpoint), Node's built-ins cover it:
`crypto.createPublicKey({ key: jwk, format: 'jwk' })` accepts an RSA JWK from
`jwks_uri`, and `crypto.verify('sha256', data, key, signature)` checks RS256
(https://nodejs.org/api/crypto.html). Or `jose`: `createRemoteJWKSet(new URL(jwks_uri))`
plus `jwtVerify(jwt, JWKS, { issuer, audience })`, which caches the key set and refetches
on an unknown `kid` after a cooldown
(https://github.com/panva/jose/blob/main/docs/jwks/remote/functions/createRemoteJWKSet.md,
https://github.com/panva/jose/blob/main/docs/jwt/verify/functions/jwtVerify.md).

## 5. Session handling

The ID token is a login receipt, not a session. After the checks in §4 pass, the service
creates its own session and forgets the Google tokens; Google's guide ends with "Query
your user database and establish a session"
(https://developers.google.com/identity/openid-connect/openid-connect). Nothing needs a
refresh token — a sign-in-only client never calls a Google API after login, so omit
`access_type=offline` (https://developers.google.com/identity/protocols/oauth2/web-server).

Two short-lived things must survive the round trip to Google: `state` and (if used)
`nonce` and `code_verifier`. The smallest store is a pre-auth cookie holding a random id
that keys an in-memory map with a short TTL; the callback reads it, checks `state`, and
deletes the entry. With one process and one operator, an in-memory `Map` for both the
pre-auth entry and the session itself is adequate; restarts log everyone out, which for
this service is fine.

Cookie attributes, from the HTTP Working Group's cookie draft
(https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis):

- `Secure` — "limits the scope of the cookie to 'secure' channels".
- `HttpOnly` — "instructs the user agent to omit the cookie when providing access to
  cookies via non-HTTP APIs" (no `document.cookie`).
- `SameSite=Lax` — sent "with same-site requests, and with 'cross-site' top-level
  navigations" using safe methods. Lax, not Strict, because the OAuth callback _is_ a
  cross-site top-level GET from `accounts.google.com`; Strict would drop the pre-auth
  cookie on that navigation and every login would fail the `state` check.
- `__Host-` prefix — requires `Secure`, `Path=/`, and no `Domain`, pinning the cookie to
  this exact host.

Session id: `crypto.randomUUID()` or `crypto.randomBytes(32)` — both stable in
`node:crypto` (https://nodejs.org/api/crypto.html). Node's `response.setHeader('Set-Cookie',
[...])` sends multiple cookies; "Use an array of strings here to send multiple headers with
the same name" (https://nodejs.org/api/http.html). Session data lives server-side keyed by
that id; nothing user-readable goes in the cookie, so no signing or encryption library is
needed.

**openid-client** does the whole flow in five calls and validates the parts people get
wrong: `discovery(new URL('https://accounts.google.com'), clientId, clientSecret)` (default
auth `client_secret_post`), `randomState()` / `randomNonce()` / `randomPKCECodeVerifier()`

- `calculatePKCECodeChallenge()`, `buildAuthorizationUrl(config, params)`, then
  `authorizationCodeGrant(config, callbackUrl, { expectedState, expectedNonce,
pkceCodeVerifier })`, and `tokens.claims()` which "Returns the parsed JWT Claims Set of an
  id_token returned by the authorization server". It "assumes runtime support of
  WebCryptoAPI and Fetch API", which Node 24 has. Sources:
  https://github.com/panva/openid-client/blob/main/README.md,
  https://github.com/panva/openid-client/blob/main/docs/functions/discovery.md,
  https://github.com/panva/openid-client/blob/main/docs/functions/authorizationCodeGrant.md,
  https://github.com/panva/openid-client/blob/main/docs/interfaces/TokenEndpointResponseHelpers.md.
  Its ID-token handling follows the §4 rule: claims (`iss`, `aud`, `exp`, `iat`, `nonce`)
  are validated; the JWS signature is not, by design, because the token came over TLS from
  the token endpoint.

**google-auth-library** is the officially blessed verifier (`OAuth2Client.verifyIdToken`
"verifies the JWT signature, the `aud` claim, the `exp` claim, and the `iss` claim",
https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), and it also
has `generateAuthUrl`/`getToken`. It drags in six dependencies including an HTTP client
and GCP-metadata probing that a relay will never use.

**Hand-rolled on built-ins** is about 80–120 lines: two `fetch` calls (token exchange;
optionally JWKS), `URLSearchParams` to build the auth URL, `crypto.randomBytes` for
`state`/`nonce`/`code_verifier`, `crypto.createHash('sha256')` for the S256 challenge,
base64url decoding of the JWT payload, and five claim comparisons. Everything it needs is
in the tables above; the OIDC spec and Google's guide list every check. What it lacks is a
second pair of eyes on the checks and the redirect-URL edge cases (error responses,
`iss` mismatch on the callback, response-mode quirks) that a certified client already
handles.

## 7. Allowlist that seeds itself from the first login

The pattern is common in self-hosted software and is stated the same way everywhere: the
first account to arrive becomes the administrator, and thereafter only administrators add
accounts.

- Gitea's installer text: "Creating an administrator account is optional. The first
  registered user will automatically become an administrator."
  (`options/locale/locale_en-US.json`, https://github.com/go-gitea/gitea)
- Immich: "The first user to register will be the admin user. The admin user will be able
  to add other users to the application." (`docs/docs/partials/_register-admin.md`,
  https://github.com/immich-app/immich); its OAuth `auto-register` setting "will
  automatically register a user the first time they sign in"
  (https://docs.immich.app/administration/oauth).
- Portainer: "Your first user will be an administrator."
  (`start/install/server/setup.md`, https://github.com/portainer/portainer-docs)
- The alternative shape is a config-driven allowlist with no self-seeding: Grafana's
  `allowed_domains` ("The user should belong to at least one domain to log in"),
  `allow_sign_up` ("Only existing Grafana users can log in with Google if set to
  false"), and `validate_hd` (https://grafana.com/docs/grafana/latest/setup-grafana/configure-security/configure-authentication/google/);
  Miniflux's `OAUTH2_USER_CREATION` ("Set to 1 to authorize OAuth2 user creation", off by
  default) (https://miniflux.app/docs/configuration.html).

Applied to a Google-backed single-operator relay:

1. Persist the allowlist as a small JSON file (or table) of `{ sub?, email, addedBy,
addedAt }` entries. Empty file means "unclaimed".
2. On a successful login (all §4 checks pass and `email_verified === true`): if the
   allowlist is empty, write `{ sub, email, addedBy: 'bootstrap' }` and continue. This is
   the seed. Otherwise require a match on `sub`, falling back to a case-insensitive
   `email` match for entries the operator typed by hand; on an email match, fill in `sub`
   so future logins match on the stable key (per §3).
3. Anyone not matched gets 403 and no session.
4. Entries are added by the operator editing the file or via an admin-only route; the
   first (bootstrap) entry is the admin.

Two guards worth the extra lines. Race: two first logins in the same instant must not
both seed — do the empty-check and the write under one lock (a single-process relay can use
a module-level promise chain, or write the file with `wx` and treat `EEXIST` as "someone
else seeded, re-read and match"). Exposure window: between deploy and the operator's first
login, whoever reaches the URL first owns the service. Close it by either seeding the
allowlist from an environment variable (`ALLOWED_EMAILS`) so the file is never empty in
production, or keeping the Cloud project in _Testing_ with only the operator listed as a
test user, in which case Google refuses everyone else before the relay sees a token
(https://support.google.com/cloud/answer/15549945). Doing both is cheap.

## Recommendation for the relay

**Flow:** OIDC authorization-code (server) flow with `scope=openid email`, `state`,
`nonce`, and PKCE S256; verify `iss`, `aud`, `exp`, `iat`, `nonce`, and require
`email_verified === true`; key the user on `sub`. No refresh tokens, no userinfo call, no
tokeninfo endpoint. Own session in an in-memory map behind a `__Host-` cookie with
`Secure; HttpOnly; SameSite=Lax; Path=/`.

**Google setup:** one Cloud project, External user type, Testing status with the
operator as a test user, one "Web application" OAuth client with the production HTTPS
callback plus `http://localhost:<port>/...` for development. No billing account, no
verification, no cost.

**Library: `openid-client` (6.x).** It is the smallest well-maintained option that owns
the whole flow rather than a slice of it: two transitive packages (`jose`, zero-dep
`oauth4webapi`), certified against the OIDC RP conformance profiles, built on the same
`fetch` and Web Crypto Node 24 already ships, and its `authorizationCodeGrant` enforces
`state`, `nonce`, PKCE and the ID-token claim checks in one call. `google-auth-library`
is heavier (six deps, HTTP client, GCP metadata) for a service that never calls a Google
API after login. `arctic` is deprecated. A hand-rolled flow on built-ins is viable and
roughly a hundred lines, but the relay's value is not in re-implementing an RP; the
certified client costs one dependency and removes the checks most likely to be subtly
wrong. Revisit the hand-rolled option only if the dependency count itself becomes a
constraint — the flow is small enough that the switch is a day's work.

**Allowlist:** JSON file of `{ sub?, email }`; first verified login seeds it when empty
(under a write lock) and becomes the admin; later logins match on `sub` then email and
back-fill `sub`; production also seeds from `ALLOWED_EMAILS` so the file is never empty
when the service is reachable.
